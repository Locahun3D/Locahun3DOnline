## A. デザイン修正

### A-1. 連絡先（電話・住所・問い合わせ）を大きく、上の方へ【優先: 高】

**現状**
- ヒーロー左のスレート（`property-detail-view.tsx` 305〜380行付近、`slateRows` 194〜222行）で TEL / MAIL / HP を `mono text-[10.5px]` の小さい文字で出している。
- 電話番号の本命表示は最下部の CONTACT カード（934行〜）まで行かないと見えない。
- 会議の指摘:「電話番号がちっちゃい」「スタジオの次に見やすくしなきゃいけないのは絶対電話番号と問い合わせフォーム」「アクセス住所ちっちぇ。もっとでかく」。

**直し方**
1. ヒーローのスレートの TEL 行の値を **16px 以上・太字**にし、タップで発信（`tel:`）。スマホは `min-h-[44px]`。
2. ヒーローの「お問い合わせ」ボタン（468〜479行）の隣に、電話番号があれば「電話する」ボタンを並べる（スマホで特に効く）。
3. 住所（ACCESS カードの住所 663〜670行、SPECS の ADDRESS 行）を **15px・font-medium 以上**にする。
4. HP の行は URL 全文ではなく「公式サイト →」のリンク表記にする（長い URL で折り返して見づらいため）。CONTACT カードの HP 行（965〜983行）も同様。

**完了条件**: 3幅で、ファーストビュー内に電話番号（あれば）と問い合わせボタンが読める大きさで見える。

### A-2. 料金を目立たせ、利用条件をアイコンで並べる【優先: 高】

**現状**
- 料金はヒーロー下部 `mono text-[24px]`（430〜466行）。PRICING カード（701〜727行）は最低利用時間・税・ロケハン費・追加費用のテキストだけ。
- RULES カード（729〜759行）は禁止事項・キャンセルの長文と、保険・立ち会いのバッジ。
- 会議の指摘:「値段だけ色変えた方が見やすい」「料金表はもうちょっと見やすく」「ルール規定はシューテストさんみたいに音出しとか、電気料とか控室とか、ある程度こっちで絞ってあげた方が」「スペースマーケットの設備品サービスコーナーみたいに、絵を使った誰でもわかるような感じ」「絵柄が大事。アイコン」。

**直し方**
1. 金額の数字（`¥{yen}`）をアクセント色（`text-accent`、ブランド `#ffb454`）にする。単位（/HR, /day）は今の控えめな色のまま。
2. **設備・条件アイコン欄**を新設し、既存のブール項目をアイコン＋短いラベルで並べる（アイコンはインラインSVG、あり＝濃色／なし＝薄色＋斜線 or 非表示）:
   - 電源（`powerVoltage`）／駐車場（`parking`）／大型搬入（`loadingDock`）／防音（`soundproofing`）／ネット（`hasInternet`）／空調（`airConditioning`）／控室（`greenRoom`）／トイレ（`restroom`）／喫煙所（`smokingArea`）／火気（`fireAllowed`）／保険必須（`insuranceRequired`）／立ち会い必須（`attendanceRequired`）
   - 置き場所は SPECS カードの上部、または PRICING/RULES の上に全幅の帯として。SPECS 表の同じ行（264〜283行）と重複するなら、表からは外してアイコン欄に一本化する。
3. 「音出し」の可否は現スキーマに項目がない。**要確認**: `soundAllowed`（音出し可否）を追加するか、`prohibitedItems` の文面で済ませるか。追加する場合は `schemas.ts` → エディター → 表示の順で入れる。
4. 禁止事項・キャンセルの長文は、句点ごとに改行して読みやすくする（`whitespace-pre-line`＋句点改行ルール）。

**完了条件**: 設備の有無が文字を読まずにアイコンで分かる。料金の数字が色で最初に目に入る。

### A-3. 「概要」と「仕様」の重複をなくす【優先: 高】

**現状**
- OVERVIEW カード（532〜586行）の本文 `description` が、SPECS 表と同じ内容（天井高・面積・設備）を繰り返しがち。
- 本文の文字色が薄い（`text-ink/60` など、`renderOverview` 51行〜）。
- 会議の指摘:「概要って仕様と一緒のことしか書いてない」「天井高5.5はどちらかといえば仕様」「他社は概要にセールス文句（2024年4月オープン、夜はライティングで昼と違う雰囲気…）を書いてる」「文字色が消えかかってる」「天井高の下がこんなに空いてるのが意味わからない」。

**直し方（コード側）**
1. 概要本文の文字色を濃くする（本文 `text-ink/85` 以上）。句点ごとに改行して表示。
2. OVERVIEW 内のミニ指標（天井高・自然光、547〜577行）の下の余白を詰める。天井高は SPECS に移すか、ミニ指標を「天井高・面積」の2つにする（自然光は A-4 で削除）。
3. 概要本文が空、または仕様の言い換えだけなら、OVERVIEW カードを小さくし SPECS を主役にする（空の時の「紹介文は準備中です」は出さない方向で検討）。

**直し方（データ側 → B-6）**: 概要は「その物件の魅力・雰囲気・使われ方」を書く欄とし、数値の仕様は書かない。

### A-4. 「自然光あり/なし」を表示から外す【優先: 中】

**現状**: OVERVIEW のミニ指標（561行）、`studio-page-blocks.tsx` の specs ブロック（172・182行）、EN版にも表示。
**会議**:「自然光がない状況はトンネルくらい」「他の会社にもない項目」「判断基準が怪しい（自然光あるのに"なし"になってる）」→ 表示しない。
**直し方**: 上記3か所から自然光の表示を削除。スキーマ `hasNaturalLight` と検索フィルタ（カタログ側で使っていれば）は当面残してよい（データ互換）。削除するかは別途判断。

### A-5. 駐車場は「あり/なし」だけ＋「詳しくは公式サイト」【優先: 中】

**現状**: `parkingValue`（229〜239行）で `parkingCapacity > 0` なら「利用可（N台）」と台数を出している。
**会議**:「台数は書かない方が無難」「オーナーが止めたいかもしれない」「ここの情報が更新されずHPだけ変わっていたら、ロケハンで違うじゃないかになる」「詳しくは公式ホームページをご覧ください。あくまで紹介サイトの立ち位置」。
**直し方**
1. 台数を表示しない。「あり／なし」のみ。
2. 駐車場・料金・ルールなど変わりやすい項目の近くに「最新情報は公式サイトをご確認ください」と公式サイトへのリンクを小さく添える（`contactWebsite` があるときのみ）。
3. `parkingCapacity` の入力欄はエディターに残してよい（非表示で保持）。

### A-6. アクセス欄を地図中心にし、施設名で開く【優先: 高】

**現状**
- ACCESS カード（656〜692行）は住所・最寄り駅のテキスト＋小さな「Google Maps で開く →」リンク（`mono text-[11px]`）。右側が余白。
- `googleMapsUrl()`（`property-presentation.ts` 10〜14行）は **座標があれば座標で**検索している → Google マップで施設として出ず、ピンだけになる（レビューも見られない）。
- 会議の指摘:「アクセスの余白スペース無駄だから Google マップのスペースにしてほしい」「Googleマップで見るボタンを分かりやすく」「座標で出ちゃう。せっかく名前で登録してるから、名前で出てくれるとレビューもいらない」。

**直し方**
1. `googleMapsUrl()` を **施設名＋住所** で検索する形に変える: `query = "${title} ${address}"`（名前が無ければ住所、住所も無ければ座標）。`title` の改行・記号は除く。関数のシグネチャに `title` を足し、呼び出し元（`property-detail-view.tsx` 196行、他にあれば全部）を直す。テストを追加（`property-presentation` のテストがあればそこへ）。
2. ACCESS カードを2カラムにして、右側に地図の埋め込み（`https://www.google.com/maps?q=<施設名 住所>&output=embed` の `<iframe>`、`loading="lazy"`、`referrerPolicy="no-referrer-when-downgrade"`）を置く。スマホでは縦積み。**要確認**: 埋め込みを使うか、静的な地図画像＋ボタンにするか（APIキー不要なのは iframe の output=embed）。
3. 「Google マップで開く」はボタン化（枠付き、14px 以上、スマホ 44px）。
4. Google マップのレビューの自前取り込み（Places API、有料）は **やらない**。施設名で開けばレビューも見られる、が会議の結論。

### A-7. ギャラリー: 拡大表示のまま前後に送れるようにする【優先: 中】

**現状**: ギャラリー（767〜798行）は `ZoomableImage` をセルごとに使っており、拡大すると1枚だけで前後送りができない。枠は `aspect-[4/3]`。
**会議**:「拡大した状態で次の画像に変えられるボタンが欲しい」「枠が4:3じゃなくて16:9なんじゃ？構図が変」。
**直し方**
1. ギャラリー全体を1つのライトボックスにまとめ、拡大中に ←／→ ボタン・キーボード矢印・スワイプで前後に送る。Esc で閉じる、枚数表示（3 / 8）。既存の `property-photo-gallery.tsx` に同等機能があれば流用。
2. セルの比率: 元写真の多くが16:9なら `aspect-[16/9]` にする。**要確認**: 実データの写真の縦横比を数件見て決める（`object-cover` で切れている構図を確認）。

### A-8. 平面図の「DL」表記を分かりやすく【優先: 低】

**現状**: 図面リンクの右端が `DL`（638〜640行）。見出しは「図面 ／ フロアプラン」。
**会議**:「DLっていうのが理解できない人がいる」「平面図ダウンロードみたいに」。
**直し方**: 「DL」→「ダウンロード」（EN: Download）。見出しを「平面図」に。ボタンらしい見た目に。

### A-9. 検索用タグをページ下部へ【優先: 低】

**現状**: ヒーローのタイトル下に、カテゴリ・種別・タグ（最大4つ）のバッジ（391〜427行）。「屋外」「交差点」「ロケーション東京」などが上に並ぶ。
**会議**:「これ検索用のタグ。上にある必要がない」「アクセスの下とかにハッシュタグにしておけば引っかかる」。
**直し方**: ヒーローには **New とカテゴリだけ**残す。種別・タグはページ下部（ACCESS の下 など）に `#タグ` 形式で全件並べる（件数制限なし）。タグはカタログ検索へのリンクにしてもよい。

### A-10. 全体の文字サイズと余白【優先: 中】

**会議**:「全体的に文字がちょっとちっちゃい」「ルール規則の余白」→ 社長判断で「余白は大事。文字が詰まっている必要はない」。
**直し方**
1. `mono text-[10px]` のラベル類を 11〜12px に、本文 14px → 15px を目安に一段上げる（3幅で崩れないこと）。
2. 余白は減らさない。ただしカード内の**意味のない空き**（A-3 の天井高の下など）は詰める。

### A-11. ヘッダー（カバー）画像が無いときの扱い【優先: 中】

**会議**:「ヘッダー忘れてる」。表示は既に「カバー画像 準備中」のプレースホルダ（500〜512行）。
**直し方**: 表示側はこのままでよい。**公開時にカバー必須**になっているか `publishablePropertySchema`（`schemas.ts` 649行付近 `cover`）を確認し、入っていなければ公開できないようにする（B-4 と連動）。

## B. AI自動入力の修正（物件データの入れ方）

物件データを公式サイト等から自動で集めて入力する作業（AIエージェント／スクリプト）が守るルール。**これらはコードではなく入力ルールだが、公開時の検査（B-7）で機械的にも止める。**

### B-1. お問い合わせの送り先（スタジオのメール）を必ず入れる【優先: 最高】
- 問い合わせフォームは `property.contactEmail` へ転送される（`src/lib/inquiry-actions.ts` 119・146行）。**空だと転送されない**（記録は残るが施設に届かない）。
- 会議で「お問い合わせがどこにも飛ばない」と指摘。原因は `contactEmail` 未入力。
- ルール: 公式サイトの問い合わせ用メールを `contactEmail` に入れる。メールが無くフォームしかない施設は、`contactWebsite` に**問い合わせページのURL**を入れる。どちらも無いなら人に確認を依頼（推測で入れない）。
- 注意: `publicPropertyEmail()` は `shibuyasq` だけメールを隠している。これは維持。

### B-2. 自然光は判定しない【優先: 中】
- 判定が誤っていた（あるのに「なし」）。A-4 で表示を外すので、入力は「不明なら false のまま」でよく、推測で埋めない。

### B-3. 画像は公式サイトの写真を使う。Portalcam の切り出しは使わない【優先: 最高】
- 会議:「ポータル感から切り出す画像使うなって言ってるのに、一回載せたらOKと判断してる」「ホームページから画像を撮ってきて」「ギャラリーこんな綺麗なのに」。
- ルール:
  1. `cover` と `gallery` は**施設の公式サイト（またはオーナー提供）の写真**。3DGS/Portalcam のレンダリングや切り出しは使わない。
  2. 画像の出どころ（元URL）を記録する（`alt` か備考）。**要確認**: `propertyImageSchema` に `sourceUrl` を足すか。
  3. 画像の利用許諾: 紹介目的で公式写真を使うことを施設に確認済みか、施設向け契約書で許諾を取る（2026-09-19 作成の施設向け契約書案に画像利用の条項を足すか要確認）。

### B-4. ギャラリーは最低6枚、ヘッダー（カバー）必須【優先: 高】
- 会議:「4枚じゃ足りない。スペースあるから最低6枚」。
- ルール: `gallery` は **カバーと重複しない写真を6枚以上**（表示側は cover と同じ src を除外している: 184〜189行）。`cover` は必須。

### B-5. 駐車場は「あり/なし」だけ。台数は入れない【優先: 中】
- A-5 と同じ理由。`parkingCapacity` は 0 のまま。

### B-6. 概要（description）の書き方【優先: 高】
- 仕様（天井高・面積・設備・料金）を書かない。
- 書くこと: 雰囲気・特徴・向いている撮影・オープン時期・時間帯による見え方など（他社は「2024年4月オープン」「夜はライティングで昼とは違う雰囲気」のような紹介文）。
- 2〜4文。句点ごとに改行。公式サイトの紹介文を丸写ししない（要約・言い換え）。

### B-7. 公開時の検査を強める（コード）【優先: 高】
`publishablePropertySchema`（`schemas.ts`）に次を追加し、満たさない物件は「公開する」で弾く（エディターに赤いエラーを出す既存の仕組みを使う）:
1. `cover.src` 必須（既存なら確認のみ）。
2. `gallery` がカバーと重複しない画像で **6枚以上**。
3. `contactEmail` または `contactWebsite` のどちらかが必須（B-1）。
4. `description` が SPECS の数値の言い換えだけになっていないかの自動判定は難しいので、ここではしない（B-6 は運用で）。
- 既存の公開済み物件（現状 `shibuyasq` 1件）が新ルールで弾かれないか確認。弾かれる場合は既存の公開状態は維持し、**次回保存時**にだけ検査がかかることを確認する。
- テストを追加（`schemas` のテスト、既存 `property-spec-*.test.ts` の近く）。

## 要確認（実装前に中村さんに聞く）

1. A-2: 「音出し可否」の項目を新設するか。
2. A-6: 地図は iframe 埋め込みか、静的画像＋ボタンか。
3. A-7: ギャラリー枠を 16:9 にするか、4:3 のままか（実写真の比率を見て提案）。
4. A-4: `hasNaturalLight` をスキーマ・検索からも消すか、表示だけ消すか。
5. B-3: 画像の出どころURLを保存する項目を足すか。施設向け契約書に画像利用の条項を足すか。

## 進め方（推奨順）

1. B-7（公開時の検査）と A-6-1（地図を施設名で開く）— 小さく効果が大きい。
2. A-1（連絡先）→ A-3（概要）→ A-4（自然光）→ A-5（駐車場）— 表示の整理。
3. A-2（料金・アイコン）→ A-7（ギャラリー）— 見た目の作り込み。
4. A-8〜A-11 — 仕上げ。
5. B-1〜B-6 は、物件データを入れている担当（AI）に本書の B 章を渡して、既存の下書き物件（Dropbox の処理済み14件ほど）に適用する。

各段階で: `npm run lint` / `npx tsc --noEmit` / `npx vitest run` → 3幅スクショ → `python scripts/design-fb-audit.py`。push はしない。
